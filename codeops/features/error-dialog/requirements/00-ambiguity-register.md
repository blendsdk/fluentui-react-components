> **Status**: ✅ GATE PASSED — all 19 items resolved

Context imported from the approved planning session: the legacy `@blendsdk/fluentui` v3 error
module (Fluent UI v8) and its `fui8` successor were analyzed; the user chose the component-only
scope (Option A) and directed the RD to be created for the feature `error-dialog`. Items 1–2 are
pre-resolved from that session and are not re-confirmed. Items 3–14 were resolved in the
discovery batch of 2026-10-16; items 3, 6, 12, 13 and 14 were the five-row packet the user
accepted in bulk (bulk acceptance is an explicit decision per the gate rules). Items 15–19 were
resolved on 2026-10-16: items 15–18 in a follow-up session that revisited the deferred provider
question (AR #1) — the user chose to ship a provider as RD-02 in this library and ruled its API
shape, capture policy and export surface; item 19 (sign-out completion) was ruled from the RD-02
preflight findings.

## Resolution Notes

**AR-1:** Capture, the singleton store and the session policy are framework/app concerns; the
component is controlled and side-effect free. This keeps the library SSR- and test-safe (the
legacy store attached its window listener at import time).

**AR-2:** Feature artifacts live under `codeops/features/error-dialog/`.

**AR-1 (annotation, 2026-10-16):** the deferred provider question was revisited: the provider is
now in scope as **RD-02** in this library (AR #15); the capture policy moved to AR #17. RD-01
itself is intentionally unchanged — its preflight pass stays valid — and remains the dialog
contract.

**AR-3–AR-14:** Resolved 2026-10-16 in the discovery batch. No complexity escalation was
triggered: the component adds no dependency, no infrastructure and no generalized mechanism; the
copy affordance uses the platform Clipboard API.

**AR-15–AR-18:** Resolved 2026-10-16 in the follow-up session (provider rulings). RD-02
follows the shape of Fluent v9's toast facility (`Toaster` + `useToastController`), with
deliberate differences (context-scoped; the hook throws outside the provider), and needs no
complexity escalation: one boolean prop plus one effect — no dependency, no infrastructure.

**AR-19:** Resolved 2026-10-16 from the RD-02 preflight findings (PF2-002/003, independently
challenged): the provider's sign-out handler clears the error first and then invokes the host
handler when defined — a missing or throwing handler can never leave the user in a blocking
modal, and last-wins is preserved for re-entrant reports.

**Approved complexity escalations:** None.
