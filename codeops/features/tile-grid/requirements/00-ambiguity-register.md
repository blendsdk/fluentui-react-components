# Ambiguity Register: tile-grid requirements

> **Status**: ✅ GATE PASSED — all 21 items resolved
> **Last Updated**: 2026-10-21 23:36
> **CodeOps Artifact Schema**: 1

This register records the decisions behind the `tile-grid` requirements. The feature replaces the
CastingAppMT `TilesList`/`ActorTile` pattern with a generic Fluent UI v9 tile-grid component for
viewing, selecting, filtering, arranging, and zooming profile pictures and photos.

The user accepted the recommended v1 package on 2026-10-20. The independent challenger returned
**Simplify** for the complexity packet; the user approved the simplified packet the same day. All 18
decisions are resolved, including the dependency, browser-test, and internal-module decisions.

## Preflight Resolutions

The requirements passed preflight on 2026-10-20. The accepted findings PF-001..PF-018 are recorded in
`00-preflight-report.md` and are reflected in the RD text. Where a preflight resolution clarifies an
entry below, the RD text and the preflight report are authoritative. The main clarifications are:
masonry uses a vertical item window over geometry-owned lanes; the public contract is one composed
`TileGridProps<T>` with a full export pin; `scrollResetKey` distinguishes filtering from paging;
reorder uses Move up/Move down actions and `reorderDisabled` covers keyboard reorder; roving focus
uses one grid entry tab stop; `isDisabled` is a separate predicate; the component accepts no image
URLs and the application owns URL validation; and zoom is controlled-only.

**AR-3:** The four layouts share one geometry contract. Every mode produces item rectangles, a
visible band/lane range, a total scroll height, an index-at-point function, and a scroll anchor by
item ID. Fixed and masonry use rows/lanes; justified uses variable-width rows; mosaic uses a dense
base grid with optional 2×2 spans.

**AR-6:** Selection is controlled-first because the application almost always seeds it. IDs are the
selection identity, not item objects. `onSelectionChange` never fires on mount or when items load.
The application prunes IDs when records are deleted; the grid preserves unknown IDs so filtered and
paged selections survive.

**AR-11:** The independent challenger returned **Simplify**. It agreed that
`@tanstack/react-virtual`, `@dnd-kit/core`, and one browser runner replace larger custom subsystems,
but found no justified need to export the generic selection/marquee modules publicly in v1. The
user approved the simplified packet on 2026-10-20.

Complexity approval evidence:

- Original goal: a v1 `TileGrid` supporting 20K items, four layouts, seeded single/multi selection,
  optional marquee, optional single-item drag reorder, optional tile-size zoom, tile actions, and
  real browser interaction quality.
- Extra system or support code: `@tanstack/react-virtual`, `@dnd-kit/core`, one browser test runner,
  and internal generic selection/marquee modules.
- Why needed: custom virtualization and drag engines would be larger than the dependencies; jsdom
  cannot verify drag, marquee, zoom anchoring, or virtualization geometry.
- Evidence: current `TilesList` renders every tile and `ActorTile` loads images through CSS
  backgrounds; `@dnd-kit/sortable` does not support virtualized grid strategies; Fluent v9 has no
  public virtualizer, drag-reorder, or marquee primitive; the Fluent Virtualizer is alpha.
- Smallest solution that still works: keep the two direct dependencies and one browser runner; keep
  generic selection/marquee modules internal; reject `@dnd-kit/sortable`, `react-window`, and the
  Fluent alpha Virtualizer.
- Extra cost: two direct dependencies, one dev test runner, Vite externalization, bundle-size
  measurement, and internal module maintenance.
- Independent verdict: **Simplify** — dependencies and one browser runner are justified; public
  selection/marquee exports are not.
- Direct user decision: **approved the simplified packet**.

**AR-12:** “Browser only” means a browser application with no SSR requirement. Desktop pointer and
keyboard are the tested v1 contract. Touch taps and scrolling work through normal browser input, but
touch-specific marquee and pinch gestures are out of v1. RTL is out of v1; logical CSS properties are
used where they cost nothing.

**AR-17:** RD-01 and RD-03 are separate because the selection/marquee module has its own contract
(selection state, range, marquee, auto-scroll) while RD-03 owns how `TileGrid` integrates that module
with focus, accessibility, and filtering. RD-02 owns geometry and rendering; RD-04 owns drag and tile
presentation.
