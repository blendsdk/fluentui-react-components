**AR-3:** `Eligibility: accessibility mechanism inside the approved status requirement; no change to the user-visible behavior.` `Decision: each loader renders a role=status, aria-live=polite, aria-atomic=true root containing a visually hidden label; the visual Spinner is wrapped in an aria-hidden indicator; the Fluent Spinner label stays visible.` `Evidence: @fluentui/react-spinner@9.8.6 associates its label via aria-labelledby and defaults to role=progressbar (useSpinner.js:42,81-82); the repository has no VisuallyHidden export; the design requires one polite announcement and no double speech.` `Rejected alternatives: Spinner label inside a status wrapper (double progressbar/status semantics and insertion-announcement risk); no live region (the legacy 35/47 unlabeled behavior); a second visible label with custom typography (duplicates Fluent layout and diverges on size).` `Strongest counterargument: an aria-hidden spinner plus a hidden duplicate label adds DOM and could be seen as redundant.` `Response: it creates a single announcement source while keeping Fluent's visual label and layout.` `Confidence: High. **AR-4:** `Eligibility: internal DOM/layout mechanism inside the approved local overlay.` `Decision: LoadingOverlay renders a relative, isolated root; a display: contents content wrapper carrying aria-busy while loading and inert when visible; an absolute inset-0 scrim with tokens.colorBackgroundOverlay; and a persistent visually hidden status outside the busy subtree. **AR-5:** `Eligibility: timing and live-region implementation.` `Decision: one internal useDelayedVisibility(active, delay) hook shared by both loaders; visibility starts false and is set by an effect after the delay (0 waits one effect); the status node is mounted before its text; LoadingOverlay uses delay 300 by default, Loading uses delay 0 by default.` `Evidence: Fluent Spinner delay hides only the spinner (shouldRenderSpinner in useSpinner.js:87), not a scrim; the challenger warns that inserting a live region with text may not announce; the repository's tests use jsdom and fake timers.` `Rejected alternatives: pass delay to Spinner (scrim would appear without a spinner); show immediately (fast-operation flash); use a layout effect (SSR warning and no need for paint-critical timing).` `Strongest counterargument: a one-effect delay means one blank frame on mount for delay=0.` `Response: the blank frame is intentional; it guarantees the status node exists before its text and avoids hydration mismatch. **AR-6:** `Eligibility: focus-management mechanism inside the approved overlay; no new modal semantics.` `Decision: capture document.activeElement when loading becomes true; when the overlay becomes visible, move focus to the overlay root only if focus is inside the content, or if the browser blurred it to body and the captured element was inside and connected; restore only when the component moved focus, the previous element is connected, and focus is still on the root or body, preferring the reveal-time element when focus moved inside during the delay and otherwise the loading-start element.` `Evidence: the focus challenger verdict was A; Chromium blurs an inert focused element to body; jsdom does not reproduce inert blur; ConfirmDialog's busy effect spans useConfirmDialog.ts:198-215 and already handles both environment behaviors; the overlay root stays inside its parent dialog's focus scope.` `Rejected alternatives: leave focus alone (keyboard restarts at the document top); a dialog-style focus trap (nothing focusable in a spinner); pointer blocking only (AT/keyboard access leaks).` `Strongest counterargument: a non-modal region overlay should announce rather than steal focus, and restoration is fragile.` `Response: focus moves only when it was inside the covered region; outside focus is untouched; restoration is ownership-guarded.` `Confidence: High.
